# Platform coding jobs

## ChatGPT subscription coding

Connect your eligible account under **Settings → AI providers → Continue with ChatGPT**, using the [local pairing helper](chatgpt-plan-sign-in.md). Reload **Settings → Platform coding** and select an account-labelled ChatGPT model in **Coding model and billing account**. Choices come from your connected account's live catalog intersected with `Api / ChatGpt:ReviewedModels`. The initial reviewed policy includes GPT-6.1 Sol and GPT-6 Astra; actual availability comes from your account. Connecting alone does not switch coding billing.

Selecting ChatGPT in the form proposes 250 requests, editable from 1 to 1,000. Saving affects new jobs. The existing 5–30 minute runtime and artifact limits still apply. Subscription jobs do not use the OpenRouter $0.40/request reservation and do not require an OpenRouter key. GitHub App and Railway setup remain required. Existing settings/jobs retain the original OpenRouter mini model unless explicitly changed.

The API snapshots the account-qualified model in each job, validates current owner/tool access and model policy, owns OAuth refresh, and calls OpenAI's public Responses endpoint with streaming and storage disabled. OpenCode receives only an expiring job capability; OAuth credentials do not enter the sandbox. Requests replay text and local function context. There is no automatic paid-provider fallback. Disconnecting, removing a reviewed model, disabling coding or revoking permission blocks subsequent inference. Errors direct the owner to reconnect or [manage plan usage](https://chatgpt.com/settings/usage). The local request allowance does not guarantee subscription entitlement. Railway compute is billed separately.

Deploy matching API/Web/Worker revisions and **rebuild the immutable coding checkpoint** before enabling subscription jobs. Existing checkpoints contain the old Chat Completions-only workload. Follow the preparation procedure below with a fresh versioned name and save the returned image identity. No new environment variables or copied OAuth tokens are needed.

Synthetic verification:

```powershell
docker build -f Dockerfile.coding-sandbox -t agentplayground-coding-sandbox:subscription .
node scripts/test-coding-image.mjs agentplayground-coding-sandbox:subscription - responses
```

This verifies the pinned OpenCode binary, synthetic Responses inference, a real shell tool edit and offline artifact export without plan/API usage. Gateway tests separately cover account/permission/policy isolation, encrypted credential dispatch, request limits and safe subscription failures. Live subscription coding remains a separate rollout check. To roll back, select the original OpenRouter model, restore 1–12 requests with a budget covering $0.40/request, and save. Pending jobs retain their selected model.

Sources: [OpenAI inference](https://developers.openai.com/siwc/token-sharing-open-source/models-and-inference), [preview requirements](https://developers.openai.com/siwc/token-sharing-open-source/preview-limitations), [OpenCode providers](https://docs.opencode.ai/docs/providers/).

If a subscription job receives one HTTP 200 followed by HTTP 400s that appear as Cloudflare 502 pages, check the API revision. The initial coding adapter omitted the required tool namespace `description` and converted all upstream request/access errors into retryable 502s. Deploy the namespace/error compatibility fix to the API. It supplies the required description, preserves HTTP 400/403/429 failures, retains only bounded schema-path diagnostics and emits the documented streaming error shape. Existing coding checkpoints remain compatible; this API fix does not require another rebuild. Start a new job after deployment; old failed jobs remain immutable. The fix's tests enforce the required namespace fields with a synthetic provider. Live subscription completion remains a rollout check.

The runner accepts explicit owner requests, runs OpenCode 2.3.2 in a Railway coding sandbox, and saves the text diff and validation checks. The GitHub App opens a draft PR or adds a commit to a tracked PR. Coding is disabled by default. See [decision 0038](../decisions/0038-platform-improvement-jobs.md) and [decision 0051](../decisions/0052-coding-job-conversations.md).

## Setup

1. Deploy the reviewed API, Web and Worker changes through the normal deployment process. The Worker owns coding sandbox execution and cleanup and needs the same encrypted configuration bootstrap and SQL transport as the [automation programs](automation-programs.md). New coding settings are database-backed; no new environment variables are required. Runtime credentials and disablement reload without restart; image changes require preparing a new checkpoint and saving its identity for new jobs.
2. Create a private GitHub App installed **only on the approved public repository**. Grant repository Contents: read/write, Pull requests: read/write, Administration: read-only (for verifying protections), and implicit Metadata: read. No webhook, user authentication, Actions, deployment or administration-write permission is needed. Save the App ID, installation ID and generated private PEM key through **Settings → Platform coding**. Do not paste private keys in chat or commit them.
3. Require at least one approval on `main`. Supported policies are classic protection enforced for administrators without an App review bypass, or an active repository ruleset applying to `main` with at least one approval and no bypass except explicit human users. Broad role/App bypasses and unsupported parent rulesets fail closed. The publisher only writes a stable `feat/platform-improvement-…` branch and creates draft PRs; it has no merge operation. Keep rebase-and-merge as the maintainer workflow. Audit external PR preview deployments: repository CI uses `pull_request` and synthetic data, but external preview services must also keep production secrets away from candidate code.
4. Prepare a versioned coding checkpoint using `PersonalAgent.Worker/Railway/prepare-coding.mjs`. Install that directory's locked SDK with `npm ci --ignore-scripts --no-audit --no-fund`. Supply JSON on stdin containing `token`, `environmentId` and a new `checkpoint` name using a secret prompt/manager, never command arguments or committed files. The script creates an isolated VM, builds `Dockerfile.coding-sandbox`, verifies OpenCode launches, records an image SHA-256, checkpoints and destroys the preparation VM. This incurs Railway compute usage. Retain only the printed checkpoint/image identities; resolve any reported cleanup failure.
5. Configure/enable the shared **Railway sandboxes** connection with the Railway token/environment and public HTTPS **API** origin. The Worker uses this connection with a separate coding checkpoint and immutable image ID. Save those coding identities in **Platform coding** and explicitly choose your billing account/model. OpenRouter needs its key; ChatGPT uses the owner connection described above. Use a dedicated OpenRouter key with a $5 account-side limit for the first live proof as an additional total limit. The gateway stores the real key encrypted; generated code gets only a short-lived job capability.
6. Select the required Linux test project/filter. The default `AgentSkillsTests` filter is a small smoke gate. Set a suitable gate for the requested task. The coding image includes the pinned .NET SDK, MAUI Android workload, Android SDK and JDK. Build `PersonalAgent.Mobile/PersonalAgent.Mobile.csproj` directly, and let `dotnet build` or `dotnet test` restore packages on a fresh checkout. Docker-dependent tests, tests that require private services, and Android device tests require a separate environment. An empty filter runs the whole selected project. Zero executed tests fails the gate.
7. Save coding enabled, then explicitly grant Owner both **Implement platform change** and **Inspect platform changes** under Integrations. Coach access is always rejected. Saving validates configuration syntax; a real start verifies GitHub access and review policy. No credentials appear in settings reads.

### When GitHub hides the ruleset bypass list

The App's Administration:read permission cannot see `bypass_actors`. Using your own GitHub account with ruleset write access, inspect `gh api repos/OWNER/REPO/rulesets/ID`. Confirm that the ruleset is active, applies to main, requires at least one approval, and has an empty bypass list or only individual `User` entries. Never attest to App, team, organization or repository-role bypasses.

In Platform coding settings, save **Verified ruleset ID** and the response's exact **updated_at** timestamp including fractional seconds and timezone (for example `2026-09-28T01:00:00.841Z` or its equivalent `2026-09-27T21:00:00.841-04:00`). Saving these fields is your confirmation of that review for the configured repository/App. Save repository/App identity first with verification cleared if changing it. Both fields may be cleared with ID 0 and an empty timestamp. Keep the App's administration permission read-only.

The publisher checks the ruleset revision at start and publication. After any ruleset edit, review and save its new revision before starting another job. Avoid editing rulesets while jobs are active. Timestamps are compared as exact instants, preserving fractional seconds; do not round or truncate them. Verification changes also invalidate publication for old job snapshots; recover deliberately rather than rerunning paid work blindly. A visible App/role bypass is rejected even with saved verification.

## Use and limits

Ask chat for one precise change and its acceptance criteria. The start tool takes a UUID request key; retrying the same key returns the same durable job, while a changed instruction is rejected. The response contains a job ID and dashboard link, not a claim that a PR already exists. **Coding jobs** shows state, bounded artifact contents, validation commands/results, sandbox cleanup, model request count and the PR link.

After a chat-started job finishes, the originating chat receives a transcript entry with its outcome, validation and PR or dashboard link. To revise a tracked PR, ask in chat to fix CI or address review feedback and include the PR link or original job ID if the target is ambiguous. The follow-up starts from the current PR head and receives bounded GitHub check output and failure annotations, or review text and inline comments. A passing revision adds one fast-forward commit to the same PR. If its head moved during execution, start a new follow-up to pick up the latest changes. Check output availability depends on what GitHub exposes. If a CI provider keeps diagnostics elsewhere, include a relevant excerpt in your request.

To resolve a merge conflict, ask the agent to rebase the tracked PR onto its base branch and include the PR link. This explicit rebase follow-up pins the branch head and base, replays the original linear commits in Railway, and runs the coding test gate on the resolved result. The publisher updates the same PR with a Git lease tied to the original head. Start a fresh rebase if the head or base moves.

Deploy the API and Worker changes and prepare a coding checkpoint labeled `io.agentplayground.coding-rebase=1` before trying this flow. The API image includes Git for guarded publication. A rebase supports up to 25 linear commits and the existing bounded regular-text artifact rules. A fully resolved replay can resume validation from a new sandbox. If the runner runs out of time while conflicts remain unresolved, inspect the phase checks and start a fresh rebase.

When OpenCode asks a question, reply in the originating chat or use **Platform changes → Outstanding questions** on the web or **Outstanding questions** in the Android menu. Registered Android devices receive a brief push with no question text. Tap it to open the outstanding questions list after signing in. Answers return to the same running OpenCode turn. The job can ask up to five sequential questions. Answer within the original runtime budget. If it expires or is cancelled, start a new job or PR follow-up and include your answer. Jobs created before conversation linking can be revised from a current conversation, which receives the new job's messages.

The lifecycle is `Queued → Running → ReadyToPublish → Publishing → PrOpened`, with `Failed` and `Cancelled` alternatives. One job can be Running at a time across runner replicas. The committed job row is durable dispatch intent: the coordinator resends Queued rows; atomic claims prevent duplicate execution. A claimed run interrupted by a restart is failed at its deadline rather than run twice. Artifacts are persisted before normal cleanup. Failed export retains phase checks when the controller can still return them; a lost VM/process can leave no artifact.

For an intentional verification run or a request that can legitimately end without a diff, ask chat to allow a no-change result. The coding tool records `allowNoChanges=true`. A clean export after successful coding and passing tests finishes as **Completed without changes**, keeps the summary and checks, and posts back to chat. Ordinary change jobs still require a diff. A timeout or failed check still fails the job. Roll out matching API, Web, and Worker revisions and prepare a fresh coding checkpoint for this behavior.

The worker has 4 GiB RAM, two CPUs, 512 PIDs, read-only root, unprivileged coding/testing, finite execution and isolated Railway networking with Internet access. No Docker socket, Railway management token, GitHub token, production database or real OpenRouter key enters the candidate container. Preparation, coding, validation and offline export use separate processes/containers with a shared workspace. The trusted image, request mount and publisher remain outside generated changes.

For OpenRouter jobs, only `openai/gpt-5.4-mini` via OpenRouter's OpenAI provider is permitted. Provider fallback, hosted tools, plugins and non-text input are rejected/removed. Provider pricing is capped at $0.75/M input and $4.50/M output, with zero per-request fee and 8,192 output tokens. Each attempt reserves $0.40 **before** dispatch, including failures, retries, title generation and compaction. At most 12 calls reserve $4.80 per job; settings may lower that limit. Reservations are conservative bounds, not billing measurements. The $5 live-proof authorization covers one proof, not unlimited new jobs. Railway compute and ordinary chat inference are separate. Model/provider unavailability fails the run; there is no alternate paid provider.

Artifacts are limited to 50 UTF-8 text files and 1 MB, matching the pinned base. Symlinks, binary files, traversal, `.git*` paths (including `.github` and `.gitignore`), keys and generated output directories are rejected. Workflow changes therefore need a separate maintainer-controlled path. The publisher never executes candidate code. Test evidence describes the selected gate; candidate tests and source remain subject to maintainer review.

## Recovery and rollback

A new coding job can use up to three fresh sandboxes. Each attempt uses the existing per-sandbox runtime setting. The overall deadline includes five minutes of queue and cleanup allowance per attempt. The model request limit applies to the whole job. The dashboard shows the attempt number and the last saved artifact. Deploy the updated API, Web and Worker and prepare a new coding checkpoint from the matching image.

The runner stops coding before the hard deadline to export a bounded text diff and progress note. The new sandbox restores the diff against the pinned base. Owner answers carry forward. An outstanding question remains answerable through chat or the dashboard. After exhausting attempts or model budget, the job shows the last saved checkpoint and failure. A provider or Worker outage can interrupt an attempt before it exports.

For broad coding requests, chat can set `supervise=true`. The coding supervisor delegates independent, read-only analysis and integrates specialist findings into one validated change. For requests that also need public research or other work, start one [supervised workflow](automations.md#supervised-workflows).

If a coding run stops immediately after a shell command with an empty HTTP 400, check API event 4406 and the retained coding output. OpenCode can replay command results as text blocks. The updated API accepts those blocks and returns a bounded diagnostic for unsupported input. Deploy the API update and switch to a fresh coding checkpoint for the Android toolchain. Previous failures retain their candidate diffs in **Coding jobs**.

Cancel from the dashboard before Publishing. Cancellation/disablement revokes new model calls and publication and stops the worker through its poll/cancellation path. A request already in flight may complete. Publishing cannot be cancelled blindly: a lost GitHub response may already have created the PR. Reconciliation uses the stable branch, deterministic commit and job marker to discover it without duplicating or overwriting the branch. Transient/ambiguous publication failures remain Publishing for retry; inspect the stable branch and GitHub App setup if this persists. Disabling blocks further publication attempts; existing PRs are not closed or merged.

Cleanup has separate state. Known sandbox IDs are saved before executing candidate code, even when provisioning races with cancellation. The reconciler retries destruction using encrypted original Railway credentials; keep rotated credentials valid until their leases are destroyed. A lost create response starts no candidate code, and Railway's five-minute idle timeout covers the unidentified VM. Controller/provider outages can delay cleanup; inspect Railway Sandboxes for unresolved jobs. Destroyed leases clear saved credentials and capability hashes. Metadata-only log events 4401–4404 identify reconciliation/execution/cleanup failures; private diff/check output stays in the owner dashboard.

Disable Platform coding and revoke its tool permissions to roll back. This leaves existing recipe automations available. Changes to skills, prompts or the platform become active only through maintainer merge and normal deployment.
