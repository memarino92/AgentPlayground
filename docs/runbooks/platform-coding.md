# Platform coding jobs

The first slice accepts an explicit owner chat request, runs OpenCode 1.18.32 in a Railway coding sandbox, retains a text diff and validation checks, and opens a draft PR through a separate GitHub App. It is disabled by default. Recurring backlog selection and PR revision are not implemented. See [decision 0038](../decisions/0038-platform-improvement-jobs.md).

## Setup

1. Deploy the reviewed API, Web and AutomationRunner changes through the normal deployment process. The runner needs the same encrypted configuration bootstrap and SQL transport as the existing [automation runner](automation-programs.md). New coding settings are database-backed; no new environment variables are required. Runtime credentials and disablement reload without restart; image changes require preparing a new checkpoint and saving its identity for new jobs.
2. Create a private GitHub App installed **only on the approved public repository**. Grant repository Contents: read/write, Pull requests: read/write, Administration: read-only (for verifying protections), and implicit Metadata: read. No webhook, user authentication, Actions, deployment or administration-write permission is needed. Save the App ID, installation ID and generated private PEM key through **Settings → Platform coding**. Do not paste private keys in chat or commit them.
3. Require at least one approval on `main`. Supported policies are classic protection enforced for administrators without an App review bypass, or an active repository ruleset applying to `main` with at least one approval and no bypass except explicit human users. Broad role/App bypasses and unsupported parent rulesets fail closed. The publisher only writes a stable `feat/platform-improvement-…` branch and creates draft PRs; it has no merge operation. Keep rebase-and-merge as the maintainer workflow. Audit external PR preview deployments: repository CI uses `pull_request` and synthetic data, but external preview services must also keep production secrets away from candidate code.
4. Prepare a versioned coding checkpoint using `PersonalAgent.AutomationRunner/Railway/prepare-coding.mjs`. Install that directory's locked SDK with `npm ci --ignore-scripts --no-audit --no-fund`. Supply JSON on stdin containing `token`, `environmentId` and a new `checkpoint` name using a secret prompt/manager, never command arguments or committed files. The script creates an isolated VM, builds `Dockerfile.coding-sandbox`, verifies OpenCode launches, records an image SHA-256, checkpoints and destroys the preparation VM. This incurs Railway compute usage. Retain only the printed checkpoint/image identities; resolve any reported cleanup failure.
5. Configure/enable the existing **Automation runner** connection with the Railway token/environment and public HTTPS **API** origin. The coding worker uses this connection but its own checkpoint and immutable image ID. Save those coding identities and an OpenRouter key in **Platform coding**. Use a dedicated OpenRouter key with a $5 account-side limit for the first live proof as an additional total limit. The gateway stores the real key encrypted; generated code gets only a short-lived job capability.
6. Select the required Linux test project/filter. The default `AgentSkillsTests` filter is only a small smoke gate, not proof that arbitrary platform changes pass all relevant tests. Set a suitable gate for the requested task. Current workers have no Docker socket or production database; tests needing Testcontainers, mobile SDKs or private services are not supported. An empty filter runs the whole selected project; zero executed tests fails the gate.
7. Save coding enabled, then explicitly grant Owner both **Implement platform change** and **Inspect platform changes** under Integrations. Coach access is always rejected. Saving validates configuration syntax; a real start verifies GitHub access and review policy. No credentials appear in settings reads.

## Use and limits

Ask chat for one precise change and its acceptance criteria. The start tool takes a UUID request key; retrying the same key returns the same durable job, while a changed instruction is rejected. The response contains a job ID and dashboard link, not a claim that a PR already exists. **Coding jobs** shows state, bounded artifact contents, validation commands/results, sandbox cleanup, model request count and the PR link.

The lifecycle is `Queued → Running → ReadyToPublish → Publishing → PrOpened`, with `Failed` and `Cancelled` alternatives. One job can be Running at a time across runner replicas. The committed job row is durable dispatch intent: the coordinator resends Queued rows; atomic claims prevent duplicate execution. A claimed run interrupted by a restart is failed at its deadline rather than run twice. Artifacts are persisted before normal cleanup. Failed export retains phase checks when the controller can still return them; a lost VM/process can leave no artifact.

The worker has 4 GiB RAM, two CPUs, 512 PIDs, read-only root, unprivileged coding/testing, finite execution and isolated Railway networking with Internet access. No Docker socket, Railway management token, GitHub token, production database or real OpenRouter key enters the candidate container. Preparation, coding, validation and offline export use separate processes/containers with a shared workspace. The trusted image, request mount and publisher remain outside generated changes.

Only `openai/gpt-5.4-mini` via OpenRouter's OpenAI provider is permitted. Provider fallback, hosted tools, plugins and non-text input are rejected/removed. Provider pricing is capped at $0.75/M input and $4.50/M output, with zero per-request fee and 8,192 output tokens. Each attempt reserves $0.40 **before** dispatch, including failures, retries, title generation and compaction. At most 12 calls reserve $4.80 per job; settings may lower that limit. Reservations are conservative bounds, not billing measurements. The $5 live-proof authorization covers one proof, not unlimited new jobs. Railway compute and ordinary chat inference are separate. Model/provider unavailability fails the run; there is no alternate paid provider.

Artifacts are limited to 50 UTF-8 text files and 1 MB, matching the pinned base. Symlinks, binary files, traversal, `.git*` paths (including `.github` and `.gitignore`), keys and generated output directories are rejected. Workflow changes therefore need a separate maintainer-controlled path. The publisher never executes candidate code. Test evidence describes the selected gate; candidate tests and source remain subject to maintainer review.

## Recovery and rollback

Cancel from the dashboard before Publishing. Cancellation/disablement revokes new model calls and publication and stops the worker through its poll/cancellation path. A request already in flight may complete. Publishing cannot be cancelled blindly: a lost GitHub response may already have created the PR. Reconciliation uses the stable branch, deterministic commit and job marker to discover it without duplicating or overwriting the branch. Transient/ambiguous publication failures remain Publishing for retry; inspect the stable branch and GitHub App setup if this persists. Disabling blocks further publication attempts; existing PRs are not closed or merged.

Cleanup has separate state. Known sandbox IDs are saved before executing candidate code, even when provisioning races with cancellation. The reconciler retries destruction using encrypted original Railway credentials; keep rotated credentials valid until their leases are destroyed. A lost create response starts no candidate code, and the 35-minute Railway idle timeout is the fallback for the unidentified VM. Controller/provider outages can delay cleanup; inspect Railway Sandboxes for unresolved jobs. Destroyed leases clear saved credentials and capability hashes. Metadata-only log events 4401–4404 identify reconciliation/execution/cleanup failures; private diff/check output stays in the owner dashboard.

Disable Platform coding and revoke its tool permissions to roll back. This leaves existing recipe automations available. Changes to skills, prompts or the platform become active only through maintainer merge and normal deployment.

## Verification

Build the local image and run `node scripts/test-coding-image.mjs`. This uses a local synthetic model server and a disposable Docker volume: it verifies real OpenCode configuration, a tool-driven file edit and offline artifact export without model charges. Supply an optional pinned public base SHA as the second argument after the image name to also verify repository checkout and the Linux test gate. Both local proof modes passed on 2026-09-27. Neither proves Railway or live OpenRouter connectivity. API tests cover owner revocation, price/request sanitization, unsafe artifacts, review policy and recovery after a lost PR-create response. Runner PostgreSQL tests cover atomic claims, concurrent budget reservations, encrypted settings and cancellation/cleanup races. Web tests cover masked secret editing and conflict/authorization errors.

Before production enablement, complete one explicitly scoped live change within the $5 model cap: verify public clone at the recorded base, real OpenRouter response, meaningful validation, retained diff, a single draft PR and sandbox destruction. Interrupt a run and verify cleanup/replay behavior before scheduling unattended work. No live Railway/OpenRouter coding proof has yet been recorded for this slice. On 2026-09-27, the repository's effective PR rule required **zero approvals**; the publisher correctly refuses that policy until tightened. GitHub App provisioning and live setup remain operator prerequisites.
